# MallX 购物车模块知识点笔记

> 本文整理自 `mall-cart` 模块开发过程中的讨论，重点记录设计原因、技术取舍和后续演进方向。
>
> 状态说明：当前实现采用 **Redis作为购物车主存储**，暂未增加MySQL购物车表；MySQL持久化方案已经讨论，但决定后续再调整。

## 1. 购物车的业务边界

购物车只负责记录用户的购买意向：

```text
用户想购买哪个SKU
购买多少件
是否勾选
何时加入购物车
```

购物车不负责：

- 创建订单
- 锁定或扣减库存
- 决定最终成交价格
- 计算会员最终优惠
- 使用优惠券
- 保存可信的商品资料

因此，购物车是商品和订单之间的临时业务状态，不是交易事实来源。

## 2. 当前Redis数据结构

当前每个登录用户使用一个Redis Hash：

```text
mall:cart:{userId}
```

Hash Field是SKU ID，Value为购物车自身状态：

```json
{
  "quantity": 2,
  "selected": true,
  "addedAt": 1787241600000
}
```

Redis中没有以下字段：

```text
salePrice
marketPrice
productName
skuName
imageOssKey
availableStock
```

这些数据分别属于商品模块和库存模块，不属于购物车。

### Redis Hash的意义

- 一个用户一个Key，天然按用户隔离。
- 一个SKU一个Field，可以单独新增、修改和删除。
- 查询一个用户的购物车只需一次 `HGETALL`。
- 不需要建立购物车MySQL表处理高频增删改。
- 用户之间操作不同Key，不会形成全局热点行。

### Redis Cluster Hash Tag

Key中的 `{userId}` 是Redis Cluster Hash Tag：

```text
mall:cart:{1001}
```

Redis Cluster只对大括号中的内容计算Slot。未来即使一个用户拆成多个购物车Key，也可以让这些Key落到同一个Slot，便于Lua或事务操作。

## 3. 为什么购物车不保存商品价格

商品价格会发生变化。如果把价格作为购物车事实数据保存到Redis，商品改价后购物车可能继续展示旧价格，还要额外设计价格同步。

当前查询流程：

```text
Redis读取SKU、数量、勾选状态
        ↓
mall-product批量查询商品当前信息
        ↓
mall-inventory批量查询当前库存
        ↓
使用当前销售价计算购物车小计
```

因此商品从100元修改为80元后，Redis购物车内容不需要变化；用户再次查询时会按80元重新计算。

### 三种价格的职责

| 价格 | 作用 | 是否可信成交价 |
|---|---|---|
| 加入购物车时价格 | 可选，仅适合以后做降价提醒 | 否 |
| 商品当前价格 | 购物车展示和结算预览 | 否 |
| 订单成交价格 | 创建订单时重新校验并固化 | 是 |

第一阶段不保存“加入购物车时价格”，暂不开发降价提醒。

### 不能相信前端价格

前端提交订单时可能篡改价格，也可能因为页面停留时间过长而携带旧价格。因此订单模块必须：

```text
重新查询商品当前价格
重新校验商品状态
重新校验并锁定库存
生成订单明细价格快照
```

订单创建后，即使商品再次改价，也不能改变历史订单成交价。

## 4. Redis是否真正发挥了作用

当前Redis解决的是购物车自身的高频状态读写：

- 加入购物车
- 修改数量
- 删除商品
- 勾选和取消勾选
- 全选和取消全选
- 用户购物车隔离
- 过期时间管理

但当前购物车查询仍会访问MySQL：

```text
Redis：查询购物车状态
MySQL：批量查询商品当前信息
MySQL：批量查询库存
```

所以准确结论是：

> Redis已经减少了购物车数据本身的数据库读写，但还没有消除商品和库存查询产生的数据库访问。

商品多级缓存暂不开发。以后增加 `Caffeine L1 + Redis L2` 后，商品信息可以优先从缓存获取；普通订单库存仍以MySQL为事实来源。

## 5. 为什么必须批量查询商品和库存

假设购物车有20个SKU，如果逐个调用商品和库存查询：

```text
20次商品查询 + 20次库存查询
```

这会形成N+1问题。

当前商品模块提供：

```java
listCartProducts(Collection<Long> skuIds)
```

该查询需要：

- 动态 `IN`
- SKU与SPU关联
- 一次返回商品名称、规格、价格和状态

因此属于复杂动态SQL，写在 `ProductSkuMapper.xml` 中。

库存模块提供：

```java
listStocks(Collection<Long> skuIds)
```

库存只是单表 `IN` 查询，使用MyBatis-Plus Lambda完成，不需要XML。

最终一次购物车查询最多包含：

```text
1次Redis Hash查询
1次商品批量SQL
1次库存批量SQL
```

## 6. 为什么使用Lua而不是分布式锁

购物车项以JSON存储。重复加入同一SKU时，如果在Java中执行：

```text
读取旧JSON
修改quantity
写回新JSON
```

两个并发请求可能同时读取相同旧值，随后互相覆盖，造成数量更新丢失。

Lua把组合操作放在Redis服务端一次执行：

```text
读取原购物车项
检查SKU种类上限
累加或覆盖数量
检查数量上限
修改勾选状态
刷新TTL
写回Redis
```

Redis执行Lua脚本期间不会穿插执行其他命令，因此该组合操作具有原子性。

这里不使用分布式锁，原因是：

- Lua已经能表达完整临界操作。
- 不需要获取、续期和释放锁。
- 不存在锁过期和误释放问题。
- 同一购物车Key的处理过程更短。

原则：

> 能用Redis原子命令或Lua完成的操作，不额外使用分布式锁。

## 7. 购物车数量和容量限制

当前约束：

```text
单个SKU最多99件
每个用户最多100种SKU
最后一次访问后30天过期
```

加入购物车时，最大允许数量还会受到当前可用库存限制：

```text
实际最大数量 = min(99, availableStock)
```

这只是购物车阶段的用户体验校验，不代表库存已经被占用。

## 8. 购物车库存校验不等于锁库存

购物车读取到库存10件后，其他用户仍然可能购买商品。因此：

```text
购物车显示有库存 ≠ 下单一定成功
```

购物车的库存作用：

- 提示售罄
- 提示数量超过当前库存
- 阻止明显无效的结算请求

真正的库存安全由订单模块完成：

```text
创建订单
  ↓
InventoryStockService.lockStock()
  ↓
MySQL条件更新成功
  ↓
库存才算真正被订单占用
```

## 9. 失效商品如何处理

购物车查询不能因为一个SKU失效而让整个购物车接口失败。

失效商品继续展示，但返回：

```text
purchasable = false
invalidReason = 具体原因
```

可能原因包括：

- 商品不存在
- SPU已下架
- SKU已下架
- 库存尚未初始化
- 可用库存为0
- 购物车数量超过当前库存

用户仍可删除失效商品，但失效商品不能进入结算。

## 10. 结算预览与订单结算的区别

购物车结算预览负责：

- 读取已勾选商品
- 校验当前商品状态
- 校验当前库存
- 查询当前价格
- 计算商品原始总额

暂不负责：

- 会员折扣
- 优惠券
- 运费
- 最终应付金额

这些规则后续统一由订单结算流程计算，避免购物车和订单分别维护一套价格规则。

## 11. HTTP接口设计知识点

购物车接口只操作当前登录用户：

```http
GET    /users/me/cart
POST   /users/me/cart/items
PATCH  /users/me/cart/items/{skuId}/quantity
PATCH  /users/me/cart/items/{skuId}/selected
PATCH  /users/me/cart/selection
DELETE /users/me/cart/items/{skuId}
DELETE /users/me/cart/selected-items
GET    /users/me/cart/checkout
```

使用 `CurrentUserProvider` 获取用户ID，不能相信前端传入的 `userId`。

数量和勾选状态属于资源的局部修改，因此使用 `PATCH`，不是完整替换资源的 `PUT`。

订单创建成功后，通过内部Service方法清理对应SKU：

```java
removePurchasedItems(userId, skuIds)
```

该方法不直接暴露给前端，防止用户绕过订单流程清理业务状态。

## 12. Redis持久化与故障问题

只使用Redis作为购物车主存储存在以下风险：

- Redis完全不可用时，当前购物车接口不可用。
- 未开启持久化时，Redis重启可能丢失全部购物车。
- RDB可能丢失最近一次快照后的数据。
- AOF `everysec` 极端情况下可能丢失约1秒数据。
- 主从、哨兵或Redis Cluster能提高可用性，但不能等同于业务持久化。

Redis自身可以通过以下能力降低风险：

```text
AOF
RDB
主从复制
Sentinel
Redis Cluster
定期备份
```

但是这些属于Redis基础设施可靠性，不能完全替代MySQL事实数据。

## 13. 讨论过的MySQL持久化方案（暂未执行）

更重视购物车长期可靠性时，可以调整为：

```text
MySQL：购物车事实数据
Redis：购物车查询缓存
```

建议表结构核心字段：

```text
id
user_id
sku_id
quantity
selected
created_at
updated_at
UNIQUE(user_id, sku_id)
```

仍然不在MySQL购物车表保存价格。

### 查询流程

```text
查询Redis
  ↓ 命中
返回购物车状态

查询Redis
  ↓ 未命中或Redis故障
查询MySQL
  ↓
条件允许时重建Redis
```

### 写入流程

如果MySQL是事实来源，应采用：

```text
先提交MySQL事务
  ↓
事务成功后删除Redis缓存
  ↓
下次查询从MySQL重建
```

不能先写Redis再写MySQL，否则可能出现Redis成功、MySQL失败的双写不一致。

### Redis故障降级

当Redis不可用时：

- 查询退化到MySQL。
- 写操作仍写MySQL。
- 记录Redis连接异常日志。
- 只捕获Redis连接类异常，不能吞掉所有业务异常。
- Redis恢复后重新构建缓存。

该方案可靠性更强，但每次购物车写操作都会访问MySQL，也需要处理缓存失效失败问题。当前决定暂不调整，后续结合项目可靠性要求和压测结果再选择。

## 14. 两种存储方案对比

| 维度 | Redis主存储（当前） | MySQL主存储 + Redis缓存（候选） |
|---|---|---|
| 读写性能 | 高 | 读高、写入需要MySQL |
| 实现复杂度 | 较低 | 较高，需要缓存一致性 |
| Redis故障 | 购物车不可用 | 可以降级到MySQL |
| 数据可靠性 | 依赖Redis持久化和集群 | MySQL作为事实来源更可靠 |
| Lua价值 | 用于原子修改购物车 | 大部分购物车Lua不再需要 |
| 适用场景 | 临时购物车、允许少量数据丢失 | 登录购物车、强调长期保留 |

没有绝对正确的统一答案，需要根据业务对性能、可靠性和复杂度的要求选择。

## 16. 面试总结

可以这样概括当前购物车设计：

> MallX购物车按用户使用Redis Hash保存SKU数量、勾选状态和加入时间，不保存商品价格。数量累加、全选等复合操作通过Lua保证原子性，不额外使用分布式锁。查询时批量调用商品与库存Service，避免N+1，并使用商品当前价格计算展示金额。购物车库存校验只用于预检查，最终成交价格和库存占用由订单模块重新校验。当前Redis是购物车主存储，后续可根据可靠性要求演进为MySQL持久化、Redis缓存以及Redis故障降级方案。
