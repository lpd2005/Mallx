# MallX 升级前后压力测试对比报告

测试日期：2026-09-11  
对比基线：`MallX_MVP压力测试报告_20260905.md`  
测试性质：同一台本地电脑上的单节点、闭环 JMeter 对比测试，不代表生产容量。

## 1. 结论摘要

- 原文档中的数据规模是 **10,000 个压测 SPU、20,000 个压测 SKU**，不是 20,000 个商品 SPU。本轮按原脚本恢复了相同规模和状态分布。
- 默认商品首页命中 JetCache 的 Caffeine + Redis 多级缓存后，平均响应从 280.14ms 降至 2.62ms，P95 从 356ms 降至 5ms，吞吐量从 178.16 次/秒提升至 13,301.41 次/秒。
- 相同关键词 `商品`、相同 50 并发和 50,000 次请求下，ES 搜索平均响应 47.86ms、吞吐量 1,034.60 次/秒；当前 MySQL `LIKE` 查询平均 232.93ms、吞吐量 213.93 次/秒。ES 吞吐量约为当前 MySQL 的 4.84 倍。
- 单商品购物车查询本轮平均响应为 23.38ms。购物车实现及其 `listCartProducts`、`listStocks` 批量查询路径没有因本次升级改为 JetCache，因此与旧版的差值只能视为同机运行波动或数据库/JVM热状态差异，不能归因于多级缓存。
- 两轮 500 人抢 100 张券均恰好成功 100 人；500 人抢 100 件库存恰好创建 100 单；100 单并发支付后库存、订单和支付记录一致，重复支付没有重复扣减。
- 热点订单成功请求平均响应比旧基线上升 14.7%，但售罄拒绝、支付单创建和支付总体接近或优于旧基线。热点数据库行锁仍是主要瓶颈，升级缓存和 ES 不会直接消除交易写入竞争。
- 所有正式 JMeter 场景的系统错误率均为 0%。

## 4. 查询性能对比

所有查询场景均使用 50 线程、1 秒 Ramp-up、每线程 1,000 次，共 50,000 次请求。

`/products` 是原有商品浏览接口，仍保留可选的 MySQL `LIKE` 关键词条件；`/search/products` 才是新搜索入口并使用 Elasticsearch。本轮故意同时压测两个入口：前者用于复现旧基线并作为 A/B 对照，后者用于验收升级后的 ES 搜索，而不是把新的搜索请求继续设计成走 MySQL。

| 场景 | 版本 | 平均 | P95 | P99 | 最大 | 吞吐量 | 错误率 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 默认商品列表 | 旧版 MySQL | 280.14ms | 356ms | 415ms | 535ms | 178.16/s | 0% |
| 默认商品列表 | 升级版 JetCache 首页 | 2.62ms | 5ms | 9ms | 214ms | 13,301.41/s | 0% |
| 宽泛关键词 `商品` | 旧版 MySQL `LIKE` | 351.28ms | 436ms | 474.99ms | 539ms | 142.09/s | 0% |
| 宽泛关键词 `商品` | 当前 MySQL `LIKE` | 232.93ms | 266ms | 385.98ms | 704ms | 213.93/s | 0% |
| 无关键词浏览 | 升级版 ES | 20.53ms | 22ms | 24ms | 607ms | 2,391.31/s | 0% |
| 宽泛关键词 `商品` | 升级版 ES | 47.86ms | 57ms | 60ms | 511ms | 1,034.60/s | 0% |
| 单商品购物车查询 | 旧版 | 31.20ms | 38ms | 42ms | 92ms | 1,590.23/s | 0% |
| 单商品购物车查询 | 当前版 | 23.38ms | 30ms | 33ms | 465ms | 2,115.51/s | 0% |

### 4.1 变化幅度

| 场景 | 平均响应变化 | P95 变化 | 吞吐量变化 |
| --- | ---: | ---: | ---: |
| 默认首页：旧版 MySQL → JetCache | 降低 99.1% | 降低 98.6% | 提升 7,366.0% |
| MySQL 宽泛查询：旧版 → 当前版 | 降低 33.7% | 降低 39.0% | 提升 50.6% |
| 宽泛查询：旧版 MySQL → ES | 降低 86.4% | 降低 86.9% | 提升 628.1% |
| 购物车查询：旧版 → 当前版 | 降低 25.1% | 降低 21.1% | 提升 33.0% |

默认首页结果来自 50,000 次完全相同的首页请求。首个请求建立缓存后，绝大部分请求直接命中当前 JVM 的 Caffeine L1，只执行缓存读取和 HTTP/JSON 响应，不访问 MySQL；因此出现一万级吞吐量是合理的热点 Key 结果。JMeter HTML 按实际样本时间窗计算为 13,301.41 次/秒，命令行包含启动收尾的整体速率约为 10,926.6 次/秒，两种口径都不是数据库吞吐量。

该结果不代表分类、品牌、关键词和非首页分页也能达到相同吞吐量，这些动态查询不会复用固定首页缓存。ES 负责全文搜索和组合过滤，多级缓存负责少量稳定热点，两者用途不同，不应只凭单个吞吐量互相替代。

当前版验账结果：

- 热点库存：可用 0、锁定 100、已售 0。

## 7. 并发支付与幂等对比

该场景先由 500 人争抢出 100 个成功订单，为其创建支付单，再同时支付，并对每个支付单重复发送一次相同通知。

| 阶段 | 旧版平均/P95 | 当前版平均/P95 | 平均变化 | 系统错误 |
| --- | ---: | ---: | ---: | ---: |
| 热点订单成功 | 未单独作为支付结论 | 280.69 / 494.75ms | - | 0 |
| 创建支付单 | 549.87 / 731.95ms | 462.91 / 652.85ms | 降低 15.8% | 0 |
| 并发模拟支付 | 306.32 / 495.75ms | 285.24 / 493.85ms | 降低 6.9% | 0 |
| 重复支付通知 | 202.24 / 387.80ms | 214.49 / 402.60ms | 增加 6.1% | 0 |

最终验账结果：

- 订单 100 条，100 条均为已支付。
- 支付记录 100 条，100 条均为已支付。
- 热点库存：可用 0、锁定 0、已售 100。
- 扣减库存流水 100 条，数量合计 100，无重复扣减流水。
- 已支付但缺少成功支付记录的订单为 0。

重复通知平均响应略有上升，但绝对差异约 12ms，且正确性完全一致。本机单轮结果不足以认定为稳定性能回退。

## 8. 升级效果判断

### 明确有效

1. **JetCache 多级缓存**显著降低固定首页热点读取成本；请求主要在本机 Caffeine 完成，不再让 50 个线程持续争抢 MySQL 连接。
2. **Elasticsearch 商品搜索**在宽泛中文关键词下显著优于 MySQL 前导通配符查询，并支持后续 nested SKU、分类、品牌、价格和库存组合检索。

### 提升有限或不直接相关

1. 优惠券领取、普通热点下单和支付仍依赖 MySQL 事务及行锁，多级缓存与 ES 不会绕过交易正确性校验。
2. 购物车核心查询代码没有改变，仍是 Redis Hash 加商品、库存批量 SQL；本轮数值只用于确认没有明显性能或正确性回退，不作为升级收益。
3. 优惠券领取代码也没有改变；两轮抢券用于复验不超发和观察本机波动，不作为缓存、ES 或秒杀升级收益。
4. 秒杀模块使用 Redis Lua、MQ 和独立秒杀入口，但旧报告没有秒杀场景，因此本报告没有把普通订单压测冒充秒杀性能对比。
5. ES 单节点 yellow 状态是本地副本无法分配造成的；性能测试通过不代表搜索集群具有高可用能力。
