# MallX MVP 压力测试报告

测试日期：2026-09-05  
测试范围：商品查询、商品模糊查询、购物车读取、限量优惠券领取、热点库存下单、模拟支付与重复支付通知。  
测试性质：本机单节点 MVP 基线测试，不代表生产环境容量结论。

## 1. 总体结论

- 商品列表在真实 50 并发、50,000 次请求下无错误，吞吐量为 178.16 次/秒，P95 为 356ms。
- 宽泛模糊查询 `LIKE '%商品%'` 同样无错误，但吞吐量比普通列表下降 20.2%，平均响应增加 25.4%。
- 单商品购物车在真实 50 并发下吞吐量为 1,590.23 次/秒，P95 为 38ms；该结果不代表包含 10～20 种商品的大购物车。
- 500 人同时争抢 100 张优惠券，两轮有效测试均恰好成功 100 人，无超发、无重复领取。
- 500 人同时争抢 100 件热点库存，恰好生成 100 个待支付订单，热点库存由可用 100 正确转为锁定 100，无超卖和重复流水。
- 100 个订单同时模拟支付后，锁定库存 100 正确转为已售库存 100；再次发送 100 次重复支付通知，没有发生重复扣减。
- 今天没有修改后端业务 Java 代码；修改内容仅为压测数据、JMeter 场景和压测说明。
- 测试过程中发现并修复了压测脚本隔离与响应分类问题，正式结论均采用修复后的有效重跑结果。

## 4. 普通查询与模糊查询对比

| 指标 | 普通商品列表 | 模糊查询 `keyword=商品` | 变化 |
| --- | ---: | ---: | ---: |
| 请求数 | 50,000 | 50,000 | 相同 |
| 并发线程 | 50 | 50 | 相同 |
| 错误率 | 0% | 0% | 相同 |
| 吞吐量 | 178.16 次/秒 | 142.09 次/秒 | 下降 20.2% |
| 平均响应 | 280.14ms | 351.28ms | 增加 25.4% |
| P95 | 356ms | 436ms | 增加 22.5% |
| P99 | 415ms | 474.99ms | 增加约 14.5% |

这组数据说明当前 1 万 SPU 下，MySQL 模糊查询仍可稳定处理 50 并发，但已经出现明显额外开销。以后接入 Elasticsearch 时，应以这一组完全相同的关键字、数据规模、线程数和请求数复测，而不是只比较不同条件下的两个结果。

## 7. 性能形成因素

高频读写能力不是单个框架决定的。本轮数据主要受以下因素共同影响：

| 层面 | 影响因素 |
| --- | --- |
| JMeter | 线程数、Ramp-up、循环次数、是否使用集合点、是否与服务同机 |
| HTTP / Tomcat | 工作线程、连接复用、请求排队、响应体大小 |
| Java | Controller 与 Service 工作量、对象创建、JSON 序列化、CPU 与 GC |
| 认证 | Sa-Token 登录态读取、Redis 网络往返、BCrypt 登录校验成本 |
| MyBatis-Plus | 是否自动执行总数查询、是否查询完整实体、SQL生成方式 |
| Druid | `maxActive`、获取连接等待时间、连接校验与数据库承载能力 |
| MySQL | 数据量、索引、过滤选择性、排序、深分页、Buffer Pool、CPU、磁盘与行锁等待 |
| Redis | Hash读取、TTL续期、连接池、网络RTT、热Key与缓存命中率 |
| 事务 | 事务中SQL数量、持锁时间、多个请求是否更新同一热点行 |
| 业务一致性 | 条件更新、唯一索引、幂等流水、重复通知处理和失败回滚 |

在固定并发的闭环测试中，可以用下式理解结果：

```text
吞吐量 ≈ 并发数 ÷ 平均响应时间
```

普通商品查询约为 `50 ÷ 0.280 ≈ 178 次/秒`，模糊查询约为 `50 ÷ 0.351 ≈ 142 次/秒`，与JMeter实测接近。

## 8. 优化优先级

### P0：先补可观测性

- 接入 Spring Boot Actuator 或等价指标。
- 记录 Druid 活跃连接、空闲连接、等待线程和获取连接耗时。
- 记录 MySQL 慢 SQL、行锁等待、Buffer Pool 命中率和 CPU。
- 记录 JVM CPU、堆内存、GC 和 Tomcat 活跃线程。
- 正式压测将 JMeter 与后端分机部署。

没有这些指标时，只能看到“请求变慢”，不能准确判断时间消耗在连接池、SQL、行锁、CPU还是网络。

### P1：优化商品高频读取

- 商品列表使用 `SpuListVO`，不查询 `description` 等详情字段。
- 不需要精确总数的页面改为多查一条并返回 `hasNext`，取消每次 `COUNT(*)`。
- 首页、热门分类第一页和商品详情增加短 TTL Caffeine 或 Redis 缓存。
- 根据 `EXPLAIN ANALYZE` 评估以下联合索引，而不是盲目新增：

```sql
(status, updated_at, id)
(category_id, status, updated_at, id)
(brand_id, status, updated_at, id)
```

- 深分页使用 `(updated_at, id)` 游标，不长期依赖大偏移量 `LIMIT offset, size`。
- 对 Druid `max-active=8/16/20` 做同场景对比，不能直接把连接数放大到 100 或 200。

### P1：保护优惠券和库存热点写入

- 保留 MySQL 条件更新、唯一索引和幂等流水，它们是当前正确性的根基。
- 增加单用户与单活动限流，避免无意义请求持续进入数据库。
- 优惠券售罄后写快速拒绝标记，减少后续请求争抢模板行。
- 缩短热点事务中非必要工作，避免持有库存或模板行锁时执行慢操作。
- 在更高流量目标下，再使用 Redis Lua 做库存预扣与一人一券，并通过 MQ 异步落库。

### P2：优化搜索

- 当前 1 万 SPU 可以继续使用 MySQL。
- 业务允许时将包含匹配改为前缀匹配。
- 需要中文全文搜索但暂不上 ES 时，可评估 MySQL `FULLTEXT ... WITH PARSER ngram`。
- 接入 ES 后必须使用相同数据和JMeter参数复测普通列表、宽泛关键词、低命中关键词、分类/品牌过滤和深分页。

### P2：支付异步削峰

- 创建支付单需要同步返回 `paymentNo`，不适合简单投入 MQ。
- 真实支付回调必须先验签、校验金额、保证幂等并可靠保存支付事实。
- 高流量下可以使用 Outbox＋RabbitMQ 异步驱动订单确认、锁定库存转已售、通知和统计。
- MQ消费者仍需依赖支付、订单和库存幂等键；MQ只削平峰值，不会减少总工作量。
- 必须补齐发送重试、重复消费、死信、对账和补偿，不能采用“提交数据库后直接发送一次消息”的不可靠方式。
