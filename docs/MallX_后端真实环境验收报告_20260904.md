## 3. 已验证的业务行为

### 认证、用户与权限

- 游客可以查询分类、品牌、商品列表以及已上架 SPU/SKU；草稿商品不允许作为前台详情读取。
- 注册产生账号和用户资料，密码保存为 BCrypt 摘要，新用户不自动成为会员或管理员。
- 非法手机号、重复手机号被拒绝；登录会话实际写入 Redis。
- 普通用户不能进入后台；只有 admin:access、没有 product:manage 的测试角色不能访问商品管理接口。
- 删除测试角色关联后，旧 Token 的后台权限立即失效；退出后旧 Token 被拒绝。
- 禁用专用测试用户后，其旧 Token 不能继续访问业务接口，随后已恢复该测试用户状态。
- 用户资料修改、地址创建、Boolean 请求参数处理和跨用户地址更新拒绝通过。
- 普通用户无法读取其他用户订单、支付单、售后单，也不能操作他人优惠券或刷新他人头像 Key。

### 商品、库存、交易与售后

- 经真实后台 API 创建分类、品牌、草稿 SPU/SKU，入库并上架。
- 相同入库单号重试不会重复增加库存；已有库存记录的 SKU 不允许删除。
- Redis 购物车添加、查询、预结算、非法数量拒绝通过。
- 下单实际锁定 MySQL 库存；订单按服务器价格计算，不能用请求中的伪造 payAmount 改价。
- 模拟支付、重复支付、备货、发货、确认收货通过。
- 待支付订单取消及重复取消通过，库存锁释放；已支付订单不能走普通取消流程。
- 已完成订单申请退货退款、审核、寄回物流、收货验收、模拟退款通过。
- 未验收退货不能退款；重复退款不会重复回补库存。
- 已支付未发货订单的仅退款流程通过；原优惠券可以在退款后重新使用。
- 后台看板、热销商品、用户、角色、审计和售后查询 SQL 成功执行。

注意：`sold_stock` 是历史累计完成扣减量，不是扣除退款后的净销量。退货回补可用库存，不冲减这个累计值；实际行为与已有售后文档一致。

### 优惠券、会员、调度与小规模并发

- 满减券创建、发布、领取、金额试算、下单锁券、支付、退款还券通过。
- 重复领取返回业务拒绝，发行计数和用户持券数均不重复增加。
- 两名用户同时竞争一张券：一人成功、一人被拒绝；数据库发行数及持券数均为 1。
- 两名用户同时购买库存只剩 1 的 SKU：一单成功、一单业务拒绝；实际库存为可用 0、锁定 1，没有负库存，随后取消成功订单释放库存。
- VIP 到期且有普通会员后备身份：恢复普通会员，95 折。
- 直接开通的 VIP 到期且无后备身份：变为非会员，原价。
- 重复查询到期会员不会重复写入到期日志；普通会员下单实际按 95 折计算。
- 对专用测试订单设置过去的到期时间，等待真实每分钟调度后，订单变为已取消、库存锁释放。

会员到期测试使用了仅针对两个专用测试账号的数据库场景数据，因为当前没有会员开通 HTTP 入口；没有把注入测试数据当成“开通会员接口验收成功”。到期调度初次查询还未到下一分钟，后来经过完整调度周期复查通过，不算业务失败。

## 4. 发现的问题及复现方式

### 问题一：路径参数类型错误返回 500

```http
GET /products/not-a-number
```

实际：HTTP 500，业务码 500，提示“系统繁忙，请稍后重试”。

期望：HTTP 400，明确提示参数格式错误。

运行时异常：`MethodArgumentTypeMismatchException`。`GlobalExceptionHandler` 没有对应分类，被 `handleUnexpectedException` 统一处理成服务器错误。

### 问题二：损坏 JSON 返回 500

```http
POST /auth/register
Content-Type: application/json

{broken-json
```

实际：HTTP 500。期望：HTTP 400。

运行时异常：`HttpMessageNotReadableException`，同样进入全局兜底异常处理。

### 问题三：错误的上传 Content-Type 返回 500

使用已登录测试用户，请求 `POST /users/me/files/avatar`，发送普通表单类型而不是 multipart/form-data。

实际：HTTP 500。期望：HTTP 415 等正确的客户端错误响应。

运行时异常：`HttpMediaTypeNotSupportedException`，没有被单独处理。

不要与“合法 multipart 中缺少 file”混淆：后者本轮实际返回 HTTP 400，测试通过。伪装成 PNG 的 SVG 文本也被 HTTP 400 拒绝，普通用户上传后台商品图被 HTTP 403 拒绝。

### 问题四：超大 multipart 请求连接中断

发送一个 6 MiB 文件，加上 multipart 边界后请求体超过配置的 6 MB 请求上限。

实际：真实 HTTP 客户端收到发送失败/连接中断，没有稳定取得完整的统一错误响应。

期望：客户端能够稳定得到约定的超限错误响应。本轮不能仅凭这个现象判断是业务异常处理、Tomcat 提前拒绝请求时的连接处理，还是客户端发送行为导致；需要针对容器和客户端继续定位。

没有证据表明超限文件被上传到 OSS。不要把“错误响应不稳定”表述成“绕过上传大小限制”。

上述问题本轮未修复。下一步可以先补齐全局异常分类及真实容器回归测试，再处理上传超限的传输行为。

## 7. 后续修复与复测

### 修改内容

1. `GlobalExceptionHandler` 分类处理路径/查询参数类型错误、空请求体、损坏JSON及JSON字段类型错误，返回HTTP 400和安全的中文提示。
2. 不支持的Content-Type返回HTTP 415，新增对应的业务码415。合法multipart缺少file仍然返回400。
3. 查询参数对象绑定失败不再透传Java类型、框架转换提示或原始错误输入。
4. `application.yml` 配置 `server.tomcat.max-swallow-size: 8MB`，保持单文件5MB和总请求6MB的上传许可不变。

大文件连接中断与Tomcat拒绝上传后排空请求体的上限有关，默认2MiB不足以覆盖此次6MiB文件及multipart边界。该设置决定拒绝后丢弃多少数据，不是允许上传多大的文件。参见[Tomcat HTTP连接器的maxSwallowSize说明](https://tomcat.apache.org/tomcat-10.1-doc/config/http.html)。

这里保留8MiB的有限排空上限，没有设置-1无限制接收。超过这一排空范围、客户端中断或网络故障，仍可能表现为连接关闭，不能保证任意大的恶意请求都收到JSON。若以后提高上传上限，需要同步评估此值；对外部署还应在入口代理限制请求体和超时。

没有新增上传Controller或改写上传服务，也没有修改Sa-Token鉴权、业务异常现有HTTP映射、MySQL结构、原Redis配置或OSS凭证。
